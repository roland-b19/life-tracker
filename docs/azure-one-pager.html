Life Tracker on Azure

Azure course project · one-page plan: the application and where each Azure service will be used

The application

Life Tracker is a personal tracker that will run as a web app and as an installable PWA on the iPhone Home Screen. It will offer tasks (daily and one-off, with streaks and push reminders), a wishlist, health tracking (weight, water, steps, nutrition), a gym log (plans, workouts, sets, progress) and a shopping list. It will hold personal and health data, so security will drive the whole design: every user will see only their own data, and no data service will be reachable from the internet.

Where each required Azure service will be used

RequirementService and its role in the app
1. ComputeAzure Container Apps. One VNet-integrated environment will run the web app and three jobs: enqueue and send (scheduled every minute) and a one-off migrate job for the database schema. Images will be deployed by digest.
2. Database / storagePostgreSQL Flexible Server will store all application data. Azure Storage will hold the reminder queue. Azure Container Registry will store the container images.
3. Secured applicationVNet with private endpoints and private DNS will keep PostgreSQL, Key Vault, the registry and the storage account off the public internet. Key Vault will keep every secret; the apps will read them through references, never from an image. Managed identities with narrowly scoped roles will replace passwords and keys; shared-key access will be switched off. Ingress will be HTTPS only.
4. Authentication and authorizationMicrosoft Entra ID will sign users in. Authorization will be enforced in the application: every record has an owner and every query and action will filter by the signed-in user. Automated tests will check that the owner is allowed and that another user and an anonymous visitor are denied.
5. Message queueAzure Storage Queue will carry task reminders. The enqueue job will write one message (ids only) for each reminder that is due; the send job will read the queue, recheck the owner and the task, and send a web-push notification to the user's phone.
6. Real functionalityThe five modules above (tasks, wishlist, health, gym, shopping), with an Apple-style dark interface, will run on Azure as one codebase that also runs on a free personal host.
7. Scripted deploymentBicep will describe every resource. A script will run read-only preflight checks; another will preview the change with what-if, ask for approval, check the cost, push the images and deploy; a third will delete the resource group. Nothing will be created by hand in the portal.
8. Cloud backend + database, securedThe Next.js backend will run in Container Apps and talk to PostgreSQL only over the private network. The PWA will act as the mobile client.

Observability and deployment (grading rubric)

ObservabilityLog Analytics will receive logs from Container Apps and diagnostics from PostgreSQL, Key Vault, the registry and the queue. An action group will e-mail the owner when one of three alert rules fires (web 5xx errors, replica restarts, queue backlog). Four saved queries will show web errors, reminder runs, queue activity and Key Vault access. A budget alert will watch the cost.
DeploymentPer iteration: deploy with the script, work, present, then tear everything down so the course credit lasts until January. An ephemeral run is expected to cost well under 1 USD.

Source of truth: infra/main.bicep, scripts/azure-*.sh, docs/requirements.md. The cost figure is an estimate.
