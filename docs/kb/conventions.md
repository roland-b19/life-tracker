# Conventions

## Working together
- The owner writes Romanian: chat replies are in Romanian. Code, comments, commit messages and PRs are in English.
- Ask before changing the stack, adding a dependency, creating any Azure resource or anything that costs money. Do nothing the owner did not ask for.
- Never run a command against the live database; never ask for a connection string, token or key in chat.
- **When the user is away:** after the user says they are away or asleep, don't wait, ask questions or ask permission until they are back. At each choice take the option you would recommend, keep going, and list the choices made in the PR body and the KB log. The user's away message can allow what normally needs their word, such as merging; the safety limits still hold.

## One way to do each job
- **Planning a feature:** the plan-feature skill, before any building.
- **Finding code:** plain search (Grep, Glob, reads) for ideas and areas, starting from the KB architecture page. Where a language server plugin is installed, use the LSP tool only when an exact location is needed: a definition, every caller or reference before changing or removing something, or the exact line to edit; never to browse. Its automatic error reports stay on. No stored code indexes.
- **Finding KB facts:** INDEX first; when it names no page, the KB search (maintain-kb SKILL.md, Search), then read the sections it points to. Grep only to list every occurrence of an exact string, such as a decision's usages.
- **Reads in a page and the session guard (D-011):** a `page.tsx` starts with `const user = await requirePageUser()` from `src/server/auth.ts` (redirects to `/signin`; gives `user.id` and `user.name`), before any data read. `RequireSession` stays the layout of every signed-in route, and the page still calls the helper. Never call `getServerSession` or `redirect("/signin")` in `app/`; `tests/pages-auth.test.ts` covers every new page and layout by itself.
- **Writes from the UI:** a `"use server"` action in `src/actions/<feature>.ts` that calls `requireUser()` first (a flagged action calls `assertClaudeEnabled()` / `assertPushEnabled()` before it), then `return respond(async () => { ... })` from `src/lib/validations/result.ts`, where the body parses with zod `.parse()` (schemas in `src/lib/validations/`, ids with `uuid` from `common.ts`) and calls `src/lib/<feature>.ts`. Every new action ships an authorization test: owner allowed, other user denied, anonymous denied.
- **Action result (D-010):** `{ success: true, ...data }` or `{ success: false, error }`; a failed `.parse()` and `throw new Refusal("message")` (expected refusals: not found, a rule of the page, a duplicate) become the failure. Never throw for something the user should read (Next hides it in production), never return `null` for "not found", never `safeParse` or a hand-written check in an action. Only `requireUser()` rejections, flag guards and real faults throw. Clients check `.success`, never "did it throw"; tests narrow with `succeeded()` from `tests/succeeded.ts` and assert refusals as `{ success: false, error }`.
- **Names:** a function that adds a row is `add<Thing>` in every layer (`src/lib`, the `...Action`, the zod schema `add<Thing>Schema` and its `Add<Thing>Input` type): never `create...`. Server actions never call `revalidatePath` (the client keeps its own state; `app/providers.tsx` refreshes the router cache once writes stop); `tests/query-count.test.ts` fails on it. The page route is `/health` to match the Health label; the liveness route is `/api/health` (D-013).
- **Imports:** `@/` is `src/` (tsconfig `paths` and the Vitest alias). A module under `src/` imported from another folder is always `@/...`, never `../`. A module in the same folder is `./x`. Root `app/` and `worker/` are outside the alias, so `app/**` reaching `app/components/` and tests loading `../app/...` or `../worker/...` use `../`; that is the only place `../` is allowed. Not enforced by lint.
- **Test auth and users:** `tests/auth.ts` holds the signed-in user and the test users. A test file mocks the auth module with `vi.mock("@/server/auth", async () => (await import("./auth")).authModule);` (the factory runs lazily, so the hoisting is no problem) and imports `authState` (`authState.id = userA` signs in, `""` is anonymous; `authState.UnauthorizedError` is the error to expect) and `seedUser(subject?)` (inserts a user, returns its id) from `./auth`. Never copy either into a test file. A test that needs a different mock (the always-anonymous mocks, `next-auth` in `query-count.test.ts`) keeps its own.
- **Undo:** every change has an Undo toast; the delete restores the row under its old id. The toast's `onUndo` is `undoWith(showToast, write, failed?)` from `app/components/toast.tsx`, never a hand-rolled block: `write` puts the screen back first, then writes, and reverts the screen itself if the write fails. It returns the action's answer (`{success}`, a boolean or nothing) or throws; a refused restore is `{success: false, error}`, so `back.success` decides whether the screen keeps the row. `undoWith` shows the "Failed to undo" warning (or `failed`, a string or a function of the answer) when the answer is falsy, `{success: false}` or a throw, and nothing when it is `true` or `{success: true}`; return `true` when there is nothing left to write and the screen is already right.
- **Form error state:** `const [errorMsg, setErrorMsg] = useState("")` (D-009). `FormModal` keeps its `error` prop; pass `error={errorMsg}`.
- **UI:** the Wishlist page (`app/wishlist/`, `app/globals.css`, `app/components/`) is the reference. Dark and light modes (the system's, or the Appearance switch in Settings, D-024), no animations except the existing ones (the dark/light fade, D-025, is one).
- **UI spacing (D-030):** inside a card the visible gap from the title to the content, and between blocks, is 1rem; a group label sits 0.25rem above its rows and groups sit 1rem apart; the last row's text sits one card padding (`--card-pad`) from the bottom edge; in a dialog a list's text starts and ends at the body's padding, the gap every dialog keeps under its title. List rows carry 0.5rem padding, so a header right before a list keeps 0.5rem and the list 0.5rem (`.section-head:has(+ …)` in `globals.css`). A big numeral or a one-line note between blocks is trimmed with `text-box: trim-both cap alphabetic` so its 1rem margins are the visible gaps. Gaps of about 24–29px between groups come from row band parity (a last row without a band), not from a different rule. Everything actionable (buttons, fields, selects, checkboxes, chips, fold arrows, collapsible titles, in forms, dialogs and sign-in too) takes `--card-edge` and `--card-shadow`, as do cards, tabs and segmented controls; tags, counts and other things you cannot act on stay flat (D-031). The turquoise buttons' edge is `--tint` mixed with `--text`, since the hairline vanishes on turquoise; disabled, Save, Log set and Send keep that edge around the secondary fill, with the `--secondary` label (D-033). A row's detail lines under its title and tag (a muscle map exercise's days, a custom exercise's equipment) use `.entry-detail` (D-032).
- **Long lists:** show 10 rows, then a More button. Two forms exist, pending the owner's choice (status, open questions): `useMore` (`app/components/lists.tsx`, More adds 10 inline; Gym history) and `useMoreDialog` (More opens a `Modal` with the full list; Health meals, D-029). A group of rows under a category title uses `GroupToggle`, which draws the title as a box (D-029).
- **Dependency versions:** caret ranges (`^x.y.z`) in `package.json` and `worker/package.json`; the lockfile pins what is installed. No new exact pin. The one deliberate exception is root `three` and `@types/three` (kept exact, `0.187.0`): 0.x libraries ship breaking changes in minor releases and a caret on 0.x does not allow a minor bump anyway, so the owner moves them by hand. Chosen by the owner on 2026-11-18.
- **Migrations:** additive Drizzle migrations with explicit GRANTs; the owner runs them on the live database before the dependent code merges.
- **Checks:** the verify skill has run at the change's test tier, the fast checks pass, and review-change has run; its PR body lists every finding as fixed or with a reason.
  - **Fast checks** (the one check command): `npm run check` (lint, typecheck, tests, KB check). Tests need Postgres, see Gotchas.
  - **End-to-end specs:** `npm run e2e` (Playwright Test, D-005), outside `npm run check` so the Stop hook stays fast; CI runs it after the fast checks. Seven specs so far: `tests/e2e/wishlist.spec.ts` (sign-in redirect, then add, Undo, delete, Undo), `tests/e2e/weight.spec.ts` (the `/health` weight card: add, edit, Undo the edit, delete, Undo the delete, each checked again after a reload), `tests/e2e/tasks.spec.ts` (`/todos`: the Today flow with Undo for each change, and a daily task showing only on the Daily tab of its own space; D-012) and `tests/e2e/gym.spec.ts` (`/gym`: start a workout, log a set, finish it, cancel it, edit a training day's routine and create or delete a custom exercise, each with Undo and checked after a reload; days are picked by name because the page selects today's day and the split has rest days; D-014), `tests/e2e/health.spec.ts` (`/health` Today and Shopping tabs: meal, nutrition goals, water and steps, and the shopping list, each with Undo and a reload check; D-015) and `tests/e2e/categories.spec.ts` (the shared categories card on Wishlist, Tasks Daily and Health shopping: one driver runs add, Undo, rename, merge and delete-with-items, each checked in the card, in the item's group heading and after a reload; D-016) and `tests/e2e/settings.spec.ts` (`/settings`: the Claude card with a fake token, a refusal, replace, disconnect and Undo for each, D-017; and the Appearance switch: Light and Dark against the other system scheme, `data-theme` and the page color, kept after a reload, Undo back to Auto, no hydration warning, D-024), each with axe on the pages it visits; `tests/e2e/helpers.ts` holds the shared `test` (with the `signedInPage` fixture), `expectNoSeriousViolations(page)` and `andSettle(page, act, body?)`. Tests tagged `@a11y` (the axe scans) run on all four projects; the rest (the flow) run on `desktop` only, because only the scan depends on the width and the color scheme: the other three projects have `grep: /@a11y/`. Each signed-in test uses the `signedInPage` fixture, which creates a dev user and deletes it afterwards (rows cascade), so a run leaves nothing behind. A step that starts a server action waits for the action's POST response (`andSettle` in `helpers.ts`) before the next step or a reload, so the spec never races the database and never waits by time. A page that reloads its list after each write sends a second action (`/gym` does not: its refresh is a GET after writes stop, so most Gym steps need no body piece; the Health page sends none either: its state stays on the client, so its spec takes the first POST and passes a body piece (`"waterMl":2500`) only where one save or Undo sends two actions, the water and steps edits); pass `andSettle` a piece of the request body (`"title":"..."`, `"isCompleted":true`) so an earlier reload is not taken for the answer, as the Tasks and categories specs do. Locator gotchas from the categories spec: a region is named by its whole heading (`Categories 1 Show categories`), so match the start (`/^Categories\b/`; the Units card on the Shopping tab starts with `Units`); `getByLabel("Category")` misses the form's select (its label text includes the options), so use `getByRole("combobox", { name })`; a shopping row is two lines (`<name>`, then `1 pcs`), found by its `Edit <name>` button; the Health `Shopping` tab is named `Shop` at phone width. The weight spec still takes the first POST (its Undo after a delete could race the same way; not seen so far). `expectNoSeriousViolations(page)` first waits for the refresh a write left due, then for a quiet `<head>` and a non-empty title, and only then scans: `app/providers.tsx` refreshes the router 600 ms after the last server action, and every refresh removes and re-adds the tags React hoists into `<head>`, the `<title>` among them, so a scan that lands in that window flags `document-title` even though the title was there a moment before (seen on `phone` in the categories spec, D-019; `next dev` also streams the title in after the content on a first load, the first cause, seen in the Tasks and Health specs). The `signedInPage` fixture follows the page's action POSTs and refresh GETs (`watchRefreshes` in `helpers.ts`) so the helper knows a refresh is due; a spec that scans after a write needs no extra step, and nothing waits by time. Nothing is excluded from the axe scans; a finding is fixed in the code, never hidden by dropping the scan or excluding a selector. Each new UI feature adds a spec or extends one. Use `getByRole`, `getByLabel` and `getByText`, auto-retrying `expect`, no time waits, and make the spec create its own user and data.
    - **Before the first run:** `docker compose up`; `npx playwright install chromium` once (about 150 MB). The test database is created and migrated by `tests/global-setup.ts` (D-018), so there is no migrate step.
    - **Deviations from the verify skill's generic text:** specs live in `tests/e2e/`, not `e2e/`; there are four Chromium projects, not three browsers; CI runs e2e, although the merge-branch `setup-github.md` reference and the verify tier table say CI runs only the fast checks. This page wins for this project: the skills stay generic, so do not "fix" CI back.
  - **Targets:** a phone-width browser (375px) and desktop Chrome, in dark and light mode. The e2e projects are `desktop` (Desktop Chrome) and `phone` (Chromium at 375×812, no touch emulation) in the dark scheme, and `desktop-light` and `phone-light`, the same two in the light scheme (Playwright's default scheme is light, so the dark ones set it). Run count: 58 tests (28 on `desktop`, the 10 `@a11y` ones again on each of `phone`, `desktop-light` and `phone-light`).
- **Risk tiers:** review-change's tier script reads the two lists below from the default branch's copy of this page; a changed file in neither list is Medium.
  - **Low:** `docs/**`, `**/README.md`, `tests/**`
  - **High:** `.github/**`, `.claude/settings*.json`, `**/hook-settings.json`, `**/*_hook.py`, `src/auth.ts`, `src/server/auth.ts`, `drizzle/**`, `drizzle.config.ts`, `infra/**`, `scripts/azure-*`, `scripts/db-init.cjs`, `Dockerfile`, `worker/**`
- **Merge on green:** off

## Gotchas
- **Next.js 16:** has breaking changes against older versions. Read the guide in `node_modules/next/dist/docs/` before changing framework-level code.
- **Postgres for tests:** `npm test` needs Postgres. Locally `docker compose up` provides it; without Docker or Postgres the DB-backed tests cannot run, and CI is the proof. Each worktree (`.claude/worktrees/<name>`) tests against its own database `life_tracker_test_<name>`, and the main folder against `life_tracker_test` (D-018), so parallel sessions never truncate each other's data. `tests/global-setup.ts` (Vitest and Playwright, not in CI) creates the database if it is missing and migrates it, from `tests/local-db.ts`. A database outlives its worktree: drop it when the worktree is removed (`DROP DATABASE life_tracker_test_<name>` as `postgres`). To use another database, run with `CI=1` and `DATABASE_URL` and `DATABASE_URL_MIGRATE` both set to it.
- **Local credentials:** the Docker passwords and `DATABASE_URL_TEST` are written only in `.env.example` (D-006). `docker compose` and `seed:dev` read your `.env`, a copy of it (`cp .env.example .env`); `tests/local-db.ts` reads `.env.example` itself, so keep `.env` in step with it. A worktree's own Postgres starts with an empty dev database, so `npm run dev` there fails to sign in (`Failed to sign in`) until `node --env-file=.env node_modules/drizzle-kit/bin.cjs migrate` and `npm run seed:dev` have run (`npm run seed:dev -- owner test` fills each named dev user, default `demo`, with sample data for every page; open Gym once first so the split exists; it never overwrites); the test databases are migrated by the specs themselves. In CI the job's env is the only source and `tests/setup.ts` has no defaults. Never write a password in code, a script or a doc.
- **Time zone:** compute "today", the weekday and the clock time with `src/lib/format-date.ts` (`APP_TZ`: `toISODate`, `weekday`, `appTime`), on the server and in client components alike. Never `new Date()` day math or a device-local API (`getDay`, `getHours`, `toTimeString`, `toLocaleDateString` without `timeZone`, and the like): the server runs in UTC and a device can be anywhere. `tests/format-date.test.ts` scans `app/` and `src/` and fails on them. `public/sw.js` and `scripts/seed-dev.cjs` are outside the scan.
- **New table:** add a GRANT for `life_tracker_app` in the migration, or the app cannot use it.
- **Postgres version:** pinned in four places that must match: `.github/workflows/ci.yml`, `.github/workflows/backup.yml`, `docker-compose.yml`, `scripts/backup-now.sh`.
- **Service worker cache:** the cache name in `app/components/page-cache.ts` must match `PAGES` in `public/sw.js`; bump `CACHE` in `public/sw.js` to refresh the muscle model.
- **Manual scripts:** `scripts/backup-now.sh` (plaintext dump of the live database into `.local/backups/`) and `scripts/import-personal.cjs` (wishlist and tasks from `.local/personal-data.json`) have no npm script or caller on purpose (D-008). Only the owner runs them, with `DATABASE_URL_MIGRATE` typed into a hidden prompt; never run them yourself. A change to `wishlist_items`, `todos` or `item_categories` must also update the importer.
- **Backup workflow:** `.github/workflows/backup.yml` must not be weakened; the private `age` key stays with the owner.
- **Health data:** never sent to an AI provider.
- **iOS 26 bottom bar:** Safari draws nothing fixed under its bottom bar and fills that strip with the plain page color, so a fixed layer near the bottom edge (the glow) looks cut off; on a screen that never scrolls, make it `position: absolute` (D-032).
- **e2e server:** the server also gets `NEXT_PUBLIC_CLAUDE_ENABLED=true` and a throwaway `CLAUDE_TOKEN_KEY` (made from a fixed string in the config, not a secret), because the Claude card on `/settings` renders only with the flag (D-017); the flag also shows the Assistant tab on `/health` in every spec, and no spec opens that tab (it needs the `claude` CLI). `AUTH_DEV` throws under a production build, so `npm run e2e` starts `next dev` on port 3100 (not `next start`) with `AUTH_DEV=true` and the local test database; the config takes `DATABASE_URL` from `tests/setup.ts` and refuses a non-local host (`CI=1` with a remote `DATABASE_URL` could otherwise reach a real database). It fails at start with Next's own message while another `next dev` runs in the same folder (stop `npm run dev` first). `next dev` also re-creates an `AGENTS.md`; it is in `.gitignore`, never commit it. `.dockerignore` lists `playwright.config.ts` because it imports `tests/setup.ts` (also ignored) and the image's `next build` typechecks every `**/*.ts` it can see; keep both ignored together. Vitest excludes `tests/e2e/**`; lint ignores `test-results/` and `playwright-report/`.
- **e2e cleanup and shared database:** the app role cannot delete users, so the `signedInPage` fixture deletes its user with `DATABASE_URL_MIGRATE` (the owner role, as the Vitest tests do); the config refuses a non-local host for both URLs. `npm run e2e` and `npm test` in one folder share its test database, and several Vitest files `TRUNCATE ... users CASCADE`: a Vitest run in the same folder during `npm run e2e` deletes the spec's user, and the add fails with a foreign-key error (`Failed to save item`). The Stop hook's `npm run check` is such a run: an agent that starts `npm run e2e` in the background and ends its turn breaks a random signed-in spec, so it waits for the run in the same turn. `npm run e2e` cannot start while `npm run dev` runs in the same checkout (Next allows one dev server per folder); to keep the owner's dev server up, commit and run it from a temporary `git worktree add --detach .claude/worktrees/<name> HEAD` beside it (`.env` copied, `node_modules` cloned with `cp -c -R`, not symlinked: Turbopack rejects that), then remove it and drop its `life_tracker_test_<name>` database. Run them one after the other; to run both at once, point the e2e run at its own local database (`CI=1` with both `DATABASE_URL` and `DATABASE_URL_MIGRATE` set to it). Another worktree's run no longer interferes (D-018).
- **e2e sign-in:** sign in through `/api/auth/csrf` and `/api/auth/callback/credentials` (`signIn` in `tests/e2e/helpers.ts`), not the `/signin` form. On that page two parallel `/api/auth/session` calls each set a CSRF cookie; a click that comes too early posts a stale token, NextAuth answers 200 without a session and the next page bounces back to `/signin`. Do not wait with `networkidle`: it is a timing guess.
- **Other worktrees:** `.claude/worktrees/**` carry their own test copies, so Vitest excludes `.claude/worktrees/**`; lint, typecheck and the Docker context exclude all of `.claude/`.
- **Language server:** the `typescript-lsp` plugin needs the global npm packages `typescript-language-server` and `typescript` (`npm install -g --ignore-scripts typescript-language-server typescript`). Installed on the owner's Mac on 2026-11-18.
