# Conventions

## Working together
- The owner writes Romanian: chat replies are in Romanian. Code, comments, commit messages and PRs are in English.
- Ask before changing the stack, adding a dependency, creating any Azure resource or anything that costs money. Do nothing the owner did not ask for.
- Never run a command against the live database; never ask for a connection string, token or key in chat.
- **When the user is away:** after the user says they are away or asleep, don't wait, ask questions or ask permission until they are back. At each choice take the option you would recommend, keep going, and list the choices made in the PR body and the KB log. The user's away message can allow what normally needs their word, such as merging; the safety limits still hold.

## One way to do each job
- **Planning a feature:** the plan-feature skill, before any building.
- **Finding code:** plain search (Grep, Glob, reads) for ideas and areas, starting from the KB architecture page. Where a language server plugin is installed, use the LSP tool only when an exact location is needed: a definition, every caller or reference before changing or removing something, or the exact line to edit; never to browse. Its automatic error reports stay on. No stored code indexes.
- **Finding KB facts:** INDEX first; when it names no page, the KB search (maintain-kb SKILL.md, Search), then read the sections it points to. Grep only to list every occurrence of an exact string, such as a decision's usages.
- **Reads in a page and the session guard (D-011):** a `page.tsx` starts with `const user = await requirePageUser("/<route>")` from `src/server/auth.ts` (redirects to `/signin?next=/<route>`, so signing in returns there; gives `user.id` and `user.name`), before any data read. `RequireSession` stays the layout of every signed-in route, called with the same path (`return RequireSession({ children, path: "/<route>" })`, not rendered as `<RequireSession>`, so the redirect runs in the layout and `tests/pages-auth.test.ts` can call it), and the page still calls the helper. `optionalPageUser()` is only for pages anyone may see (the 404 page), never a guard. Never call `getServerSession` or `redirect("/signin")` in `app/`; `tests/pages-auth.test.ts` covers every new page and layout by itself.
- **Writes from the UI:** a `"use server"` action in `src/actions/<feature>.ts` that does `return respond(async () => { const userId = await requireUser(); ... })` from `src/lib/validations/result.ts`, `requireUser()` the first line inside it, so a signed-out caller gets `{ success: false, error: SIGNED_OUT }` ("You're signed out. Sign in again.") instead of a 500 (a flagged action calls `assertClaudeEnabled()` / `assertPushEnabled()` before `respond`). An action takes one input, `rawInput: unknown` (an object, never positional arguments or a TypeScript-typed input), and the body parses it with its zod schema's `.parse()` (schemas in `src/lib/validations/`, ids with `uuid` from `common.ts`) and calls `src/lib/<feature>.ts`; the input names the row it acts on `id` (`{ id, isBought }`, never `itemId`), while a field that points at another row keeps its own name (`addSetAction({ sessionId, … })`: the set is the new row); a delete takes only the id, named `id` (`deleteXAction(id: string)`, parsed the same way; the exceptions are `deletePushSubscriptionAction(endpoint: string)`, since a subscription's key is its endpoint, and `deleteCategoryAction` and `deleteShoppingCategoryAction`, which take `rawInput` since a category's key is its name), and an action with no input takes nothing (`disconnectClaudeAction()`). `tests/static-rules.test.ts` fails on an exported action with another parameter list (D-047); it does not read the input's field names (`tests/food.test.ts` and the other action tests catch a renamed field) nor where the parse sits. Every new action ships an authorization test: owner allowed, other user denied, anonymous denied.
- **Action result (D-010):** `{ success: true, ...data }` or `{ success: false, error }`; a failed `.parse()` and `throw new Refusal("message")` (expected refusals: not found, a rule of the page, a duplicate) become the failure. Never throw for something the user should read (Next hides it in production), never return `null` for "not found", never `safeParse` or a hand-written check in an action. `respond()` also turns an `UnauthorizedError` from `requireUser()` inside it into the SIGNED_OUT failure; only flag guards and real faults throw. Zod issues reach the page as people's messages (`z.config` in `result.ts`: "Required", "Must be a number", "Too long (max N)") unless the schema gives its own. Clients check `.success`, never "did it throw"; tests narrow with `succeeded()` from `tests/succeeded.ts` (a pure success is `succeeded(await action(...))`, never `toEqual({ success: true })` or `toMatchObject({ success: true })`; `tests/result.test.ts` fails on a hand narrowing, `if (!x.success) throw` or `x.success ? x.…`/`x.success && x.…`) and assert a refusal with its message, `expect(answer).toEqual(refused(error))` with `refused()` from the same file, never `.success).toBe(false)` or `toMatchObject({ success: false })` (`tests/result.test.ts`, which specifies the answer itself, spells the shape out).
- **Shared messages and checks (U6):** a name taken already answers `alreadyExists(name)` from `src/lib/validations/result.ts` (`"<name>" already exists.`); at most two decimals is `twoDecimals` with `TWO_DECIMALS`, a date after now `FUTURE_DATE`, an edit that changes nothing `NOTHING_TO_SAVE`, all from `src/lib/validations/common.ts`. The Gym editor's new-exercise form checks a name with `exerciseNameProblem(name, known)` (`app/gym/day-editor.tsx`), in the server's words. `tests/result.test.ts` ("a refusal or check several actions give is written once") fails when these words are written in a second file.
- **Message full stops:** a field message (what a form shows under or next to a field) ends with no full stop ("Name is required"); a state refusal (gone, changed elsewhere, signed out, already exists) is a sentence and keeps its full stop. `tests/static-rules.test.ts` ("field messages end with no full stop") lists the only strings in `src/lib/validations` that end with one and fails on a `setErrorMsg` in `app/` whose text ends with one.
- **Names:** one verb per job, in every layer (`src/lib`, the `...Action`, the zod schema and its input type). A function that adds a row is `add<Thing>` (`add<Thing>Schema`, `Add<Thing>Input`), never `create...` or `log...` (`addMeal`, `addWorkoutSet`, `addSessionAction`); one that creates or changes a row (an upsert) is `save<Thing>` (`saveWeightEntry`, `saveWeightSchema`, `SaveWeightInput`). `tests/static-rules.test.ts` fails on an exported `log...` or `create...` name in `src/lib` or `src/actions` (D-047). Server actions never call `revalidatePath` (the client keeps its own state; `app/providers.tsx` refreshes the router cache once writes stop); `tests/query-count.test.ts` fails on it. The page route is `/health` to match the Health label; the liveness route is `/api/health` (D-013).
- **Imports:** `@/` is `src/` (tsconfig `paths` and the Vitest alias). A module under `src/` imported from another folder is always `@/...`, never `../`. A module in the same folder is `./x`. Root `app/` and `worker/` are outside the alias, so `app/**` reaching `app/components/` and tests loading `../app/...` or `../worker/...` use `../`; that is the only place `../` is allowed. Not enforced by lint.
- **Exports:** a helper may be exported for its own unit test; nothing else stays exported unused (D-047).
- **Test auth and users:** `tests/auth.ts` holds the signed-in user and the test users. A test file mocks the auth module with `vi.mock("@/server/auth", async () => (await import("./auth")).authModule);` (the factory runs lazily, so the hoisting is no problem) and imports `authState` (`authState.id = userA` signs in, `""` is anonymous; `authState.UnauthorizedError` is the error to expect) and `seedUser(subject?)` (inserts a user, returns its id) from `./auth`. Never copy either into a test file. A test that needs a different mock (`next-auth` in `query-count.test.ts`) keeps its own; an always-anonymous test uses the shared mock and leaves `authState.id` empty (`actions-anonymous.test.ts`).
- **Undo:** every change has an Undo toast; the delete restores the row under its old id. The toast's `onUndo` is `undoWith(showToast, write, failed?)` from `app/components/toast.tsx`, never a hand-rolled block: `write` puts the screen back first, then writes, and reverts the screen itself if the write fails. It returns the action's answer (`{success}`, a boolean or nothing) or throws; a refused restore is `{success: false, error}`, so `back.success` decides whether the screen keeps the row. `undoWith` shows nothing when the answer is `true` or `{success: true}`; a refusal (`{success: false, error}`) shows `failed` (a string or a function of the answer; by default the refusal's `error`) as a warning with no Retry, since the server has answered (D-047); no answer (a throw, `null`, `undefined` or `false`) shows `failed` ("Failed to undo" by default) with a Retry that runs the restore again; return `true` when there is nothing left to write and the screen is already right.
- **Double taps (D-043):** a button that writes acts once per tap burst through the one shared guard, `useOnce()` in `app/components/once.ts` (one write at a time per target, a row's key or one opening of the form, so a tap on another row's button still writes; then the tapped spot swallows clicks for 500 ms, never the toast's); `FormModal` uses it for Save, the food chat for Send (`once("chat", …)`). Never a component's own lock or debounce. A `busy` flag may disable and label controls; it is never the guard (D-047). Sign-in (not a server action), Gym's page-wide `busy` (every Gym control waits for the workout write), Health's `waterSaving` (the water taps wait while a water form's save is out, as they send the total on screen) and the day editor's `creating` (while "Create and add" is out, its fields wait and the day's Save waits for the exercise it adds) are such flags.
- **Busy flags (D-047):** `FormModal` shows its own saving state: while the save of the opening on screen is unanswered, Save says "Saving..." and the fields sit in a disabled `fieldset`; a form passes `keepsOpening`, so opened again before that answer it goes on as the same opening and waits, when its save sends the values it opened with as `from` (D-040; a second save would be refused, D-043), or when a second save from a fresh opening would undo the first (the day editor, the deload form, and the custom exercise and shopping item forms, whose saves send the whole form: a fresh opening shows the values from before the save). A form that passes it stays mounted while closed (the day editor: one per day), or it cannot keep its opening. A kept opening shows again the values it sent, disabled until the answer, so a refusal leaves them to fix: such a form sets its fields only in FormModal's `onOpen`, which runs as a fresh opening starts (before it paints) and not when a kept one shows again, never in the click that opens it, and keeps its fields while closed (per form: the water and steps forms each have their own). A form that edits one of several things passes `subject` (the category, the exercise or the item's id; "" for an add): opened for another one while a save is out, it is a fresh opening, and opened for the save's one again after that, it is the save's opening again; such a form also passes `snapshot` (its fields as it sends them, taken at each Save), and `onOpen` gets them back to put in the fields. A page keeps no `busy`/`saving` flag of its own for a form, and FormModal takes none. `tests/static-rules.test.ts` ("a migrated form leaves its saving state to FormModal") fails on a `busy` passed to any FormModal in `app/`, and ("a FormModal whose save sends a compare-and-set from holds Save while it is out") on any form in `app/` whose save sends a `from` and does not pass `keepsOpening`; any other form may pass it. It reads each file's syntax tree with the TypeScript compiler, as `tests/toast.test.ts` does: the handler `onSubmit` names (or the one name an inline arrow only calls) is looked up by scope and must be a function of the same file, in any shape (`function`, arrow, function expression, `useCallback`), or it fails as unknown (such as a prop); another inline function is read as itself. A FormModal under a local name (`const Modal = FormModal`, directly or chained) is checked too. It reads the handler and, however deep, follows at least these flows, each name looked up by scope in the same file (a `var` in its whole function): calls to functions of the file; a name's declaration and every write to it (an assignment to it or a member of it and, for a name that is not a function, a call or JSX prop it is handed to or a method called on it); a `useState` or `useReducer` value's setter calls, plain or destructured (`[{ value }, setForm]`), and the call a setter is handed to (`load(setInput)`, `.then(setInput)`); a callback's parameter, read as the call it is handed to (`getDraft().then((d) => …)`) or, handed to a JSX prop, as that element's component; a `for…of` or `for…in` variable, read as its iterable; a component of the file handed a value or setter in JSX; parameter defaults. Any other flow is not followed, for example: code from another file (an import, what a prop runs, a namespace member such as `<B.FormModal>`), a FormModal imported under another name, an alias of a setter, a callback or setter inside an options object (`load({ done: (v) => setInput(v) })`), a custom hook of the file, and a value aliased then changed through the alias. This reads more than a save may run, so a form that sends no `from` can be flagged. It may also read more than this list, which can only flag more; two known examples: a write keyed by a name (`table[key] = …` counts as a write to `key`), and a `catch (x)` parameter resolving to an outer `x`. A `from` counts written before `to` or after it (`{ to, from }`), not under a quoted key, set in a separate statement from `to` (`o.from = x; o.to = y`) or more than 60 characters away.
- **Adds made on the device (D-040):** an add sends `id: crypto.randomUUID()` (`newId` in `src/lib/validations/common.ts`); the insert uses it with `on conflict do nothing` and answers success, so a repeat after a lost answer adds nothing; the answer then says `repeated: true`, and the page's toast says `Already added "<name>"` (shopping) or `Already saved` (meal, weight), without an Undo. `FormModal` makes the id once per opening and hands it to `onSubmit` as `{ id }` (D-047), kept across a retry; a form inside a form (the day editor's new exercise, `app/gym/day-editor.tsx`) makes its own id when it opens, and its name check skips that id, as the refresh after a lost answer already lists the row (D-047); an add that merges into a row already there (shopping, D-042) gives that row the add's id. Categories are keyed by name and take no id (D-045).
- **Server data in a client list (D-034):** a client component keeps what the page sent in `useServerState(initial, { editing, onDeleted })` from `app/components/server-state.ts`, never a plain `useState(initial)`: a refresh replaces it, and an open edit form on a row that is gone closes with "This item was deleted.".
- **Refreshes (D-034):** `app/providers.tsx` is the one place that refreshes the router, except sign-out (`app/components/navigation.tsx`) and the sign-in form (`app/signin/signin-form.tsx`), which each refresh once right after the session changes. It refreshes 600 ms after the last write, in the other tabs of the browser through a `BroadcastChannel`, on focus or becoming visible (not within 2 s of the last refresh or load), every 60 s while visible, and at 00:00 `Europe/Bucharest` (`watchDay` in `app/components/day-watch.ts`); a refresh that comes due while offline runs once the device is back online (the window's `online` event, or the next trigger) and `/api/health` has answered (`cache: "no-store"`; the service worker never answers it; a check that fails tries again 3 s later, up to 3 times in a row, a count that starts over on an answer or a new `online`), because Next turns a refresh that fails into a full page load, which would drop an open form. The browser keeps a copy of each page seen (`staleTimes` in `next.config.ts`: 120 s for visited pages, 300 s for the tab bar's prefetches), and only a refresh drops it, so a tap on a link of the app while a write is unanswered, while a refresh is due (after this tab's write or another tab's) or while a refresh missed offline has not run yet, waits: the refresh runs at once after the answer (not 600 ms later), or once `/api/health` answers after a missed one, and the tap goes through as soon as the refresh request has started, at most 10 s after the tap (`HOLD`), so a write that never answers cannot keep the app on one page; offline, or when that check fails, it goes through at once (the copy is all there is). Only the latest tap waits: a tap on another link of the app takes its place. Any other tap or key meanwhile (a `pointerdown` or `keydown` not on the waiting link, caught on the document in the capture phase) forgets it, and the tab bar shows the page on screen again; a waiting link that has left the page (the More menu was closed) is forgotten too. These go through at once and never wait: a click with cmd, ctrl, shift or alt, a middle click, a link with a `target` other than `_self` (such as `_blank`) or with `download`, and a link that leaves the app. A write without an answer says "You're offline. Nothing was saved." or "Couldn't confirm the change. Reloaded.". Each refresh of the page on screen carries its number in an `x-refresh` header (`useRefreshesSent()` gives the function that returns the last one sent). Next sends a write without waiting for a refresh on its way and applies that refresh only after the write's own change is on screen, so a refresh the server rendered before the write puts back what it changed until the next refresh (one always follows a write). Where that must not show, the page renders the number back: the Gym page (`app/gym/page.tsx`) does, and `app/gym/use-workout.ts` sets aside a server value rendered for a refresh sent before the answer of the last write that put a workout in hand (Start, Resume, an Undo of Finish or Cancel), so such a value never ends the workout in hand; a later value without that workout ends it, with the toast, even when the value before had none either.
- **A refused Gym write (D-039):** each write of the workout in hand answers a refusal through `refused(id, error)` in `app/gym/use-workout.ts`: `WORKOUT_FINISHED` or `WORKOUT_GONE` takes that workout off the screen at once with one toast, `WORKOUT_ENDED_ELSEWHERE`, and a notes save queued behind the refused one (the one Exit, Finish or Cancel sends first) then sends nothing, nor does the write it was for; any other refusal is a warning toast and the workout stays. After a `NOTES_CHANGED` refusal the next server data gives the notes the next save changes from, and the field shows the server's notes and the typed text joined with one space (the field is one line), unless the server has none or the field holds them already (D-047).
- **Signals inside one tab (D-044):** a React context with a hook in `app/providers.tsx` (as `ToastContext`, `usePageNotOpened` and `useRefreshesSent`), never a `window` event.
- **View controls per device (D-041):** `useDeviceState(key, fallback)` from `app/components/device-state.ts` (`localStorage`), never a hand-written storage read. The Appearance choice is kept the same way (`useTheme()` in `app/components/appearance-card.tsx`) and applied by `ShellListeners` (D-047); only the theme's head script in `app/components/theme.ts` reads the storage itself, before React (`tests/static-rules.test.ts` fails on any other `localStorage` in `app/`). `sessionStorage` `sw-reload` in `app/providers.tsx` is the service worker's per-tab loop guard, not a view control.
- **Number fields (D-037):** `formatNumber`, `formatAmount` (a measured amount with no trailing zeros), `parseNumberInput` and `NOT_A_NUMBER` from `src/lib/number-format.ts` (shown and typed as `1.500,5`). A value kept or added up is rounded with `roundTo(value, decimals)` from the same file (U4); `tests/result.test.ts` ("rounds to decimals only in roundTo") fails on a `Math.round(...) / 10…` or a `Math.round(x * 10…)` anywhere else.
- **Undo keys:** a toast with Undo names the rows it touches, `touches: ["<table>:<row id>"]` (`<table>:*` for a whole list); a newer toast touching one of them takes the older one's Undo away. Keys use row ids, never names (D-045); `tests/toast.test.ts` fails on an Undo toast in `app/` that names none; the theme toast names the key the device keeps it under, `THEME_STORAGE` (D-047). Pass `saved` (the write's promise) so a failed write removes its success toast. A toast shows when the screen shows the change (D-047): an optimistic write toasts at once (with `saved`), a waiting write after its answer (without).
- **Form error state:** `const [errorMsg, setErrorMsg] = useState("")` (D-009). `FormModal` keeps its `error` prop; pass `error={errorMsg}`. `tests/static-rules.test.ts` fails on a page that starts it as `null`. An answer belongs to its opening (D-047): `onSubmit` gets `stillOpen`, and a refusal shows in the form while `stillOpen()`, else as a warning toast, so a late answer never marks or closes a form opened since: every form says it through `refusal(stillOpen, setErrorMsg, warn)` (`app/components/forms.ts`), never a copy of that test. An action inside the form (the day editor's "Create and add") gets the same `stillOpen` from FormModal's children written as a function, `{({ stillOpen }) => …}`, and its answer changes the form only while that opening is on screen. An edit form finds the fields it changed with `changedFields(from, to)` (`app/components/forms.ts`: Tasks, Wishlist, the Health water, steps and goals), never a copy of it.
- **UI:** the Wishlist page (`app/wishlist/`, `app/globals.css`, `app/components/`) is the reference. Dark and light modes (the system's, or the Appearance switch in Settings, D-024), no animations except the existing ones (the dark/light fade, D-025, is one). Every visual rule, with an ID and a light and dark example, is in `docs/design/design-system.html`: check new UI against it and update it in the same change as `app/globals.css`. Files in `docs/design/` named `OLD-…` are history, never a source. `docs/design/design-rules-general.html` is a project-agnostic snapshot for new projects, not kept in sync.
- **UI spacing (D-030):** inside a card the visible gap from the title to the content, and between blocks, is 1rem; a group label sits 0.25rem above its rows and groups sit 1rem apart; the last row's text sits one card padding (`--card-pad`) from the bottom edge; in a dialog a list's text starts and ends at the body's padding, the gap every dialog keeps under its title. List rows carry 0.5rem padding, so a header right before a list keeps 0.5rem and the list 0.5rem (`.section-head:has(+ …)` in `globals.css`). A big numeral or a one-line note between blocks is trimmed with `text-box: trim-both cap alphabetic` so its 1rem margins are the visible gaps. Gaps of about 24–29px between groups come from row band parity (a last row without a band), not from a different rule. Everything actionable (buttons, fields, selects, checkboxes, chips, fold arrows, collapsible titles, in forms, dialogs and sign-in too) takes `--card-edge` and `--card-shadow`, as do cards, tabs and segmented controls; tags, counts and other things you cannot act on stay flat (D-031). The turquoise buttons' edge is `--tint` mixed with `--text`, since the hairline vanishes on turquoise; disabled, Save, Log set and Send look like the secondary buttons (their fill and hairline), with the label faded to `--text` at 45% like any disabled button (D-033). A row's detail lines under its title and tag (a muscle map exercise's days, a custom exercise's equipment) use `.entry-detail` (D-032).
- **Long lists:** show 10 rows, then a More button: `useMoreDialog(list, title, row)` from `app/components/lists.tsx`, where More opens a `Modal` with the whole list drawn with the same `row` (Health meals, D-029; Gym history, D-047). A row whose toggle names its details (`aria-controls`) gives them another id in the dialog, as both lists are on the page at once. A group of rows under a category title uses `GroupToggle`, which draws the title as a box (D-029).
- **Dependency versions:** caret ranges (`^x.y.z`) in `package.json` and `worker/package.json`; the lockfile pins what is installed. No new exact pin. The one deliberate exception is root `three` and `@types/three` (kept exact, `0.187.0`): 0.x libraries ship breaking changes in minor releases and a caret on 0.x does not allow a minor bump anyway, so the owner moves them by hand. Chosen by the owner on 2026-11-18.
- **Migrations:** additive Drizzle migrations with explicit GRANTs; the owner runs them on the live database before the dependent code merges.
- **Checks:** the verify skill has run at the change's test tier, the fast checks pass, and review-change has run; its PR body lists every finding as fixed or with a reason.
  - **Fast checks** (the one check command): `npm run check` (lint, typecheck, tests, KB check). Tests need Postgres, see Gotchas.
  - **Unit tests:** unit tests reset the database with `resetDb` (`tests/db.ts`); `tests/result.test.ts` fails on a `TRUNCATE` anywhere else under `tests/` (D-047).

## Gotchas
- **Next.js 16:** has breaking changes against older versions. Read the guide in `node_modules/next/dist/docs/` before changing framework-level code.
- **Postgres for tests:** `npm test` needs Postgres. Locally `docker compose up` provides it; without Docker or Postgres the DB-backed tests cannot run, and CI is the proof. Each worktree (`.claude/worktrees/<name>`) tests against its own database `life_tracker_test_<name>`, and the main folder against `life_tracker_test` (D-018), so parallel sessions never truncate each other's data. `tests/global-setup.ts` (Vitest and Playwright, not in CI) creates the database if it is missing and migrates it, from `tests/local-db.ts`. A database outlives its worktree: drop it when the worktree is removed (`DROP DATABASE life_tracker_test_<name>` as `postgres`). To use another database, run with `CI=1` and `DATABASE_URL` and `DATABASE_URL_MIGRATE` both set to it. A file that opens no database, such as `tests/static-rules.test.ts`, runs with no Postgres at all: `env CI=1 DATABASE_URL=postgres://nobody:x@127.0.0.1:1/none DATABASE_URL_MIGRATE=postgres://nobody:x@127.0.0.1:1/none npx vitest run tests/static-rules.test.ts`.
- **Local credentials:** the Docker passwords and `DATABASE_URL_TEST` are written only in `.env.example` (D-006). `docker compose` and `seed:dev` read your `.env`, a copy of it (`cp .env.example .env`); `tests/local-db.ts` reads `.env.example` itself, so keep `.env` in step with it. A worktree's own Postgres starts with an empty dev database, so `npm run dev` there fails to sign in (`Failed to sign in`) until `node --env-file=.env node_modules/drizzle-kit/bin.cjs migrate` and `npm run seed:dev` have run (`npm run seed:dev -- owner test` fills each named dev user, default `demo`, with sample data for every page; open Gym once first so the split exists; it never overwrites); the test databases are migrated by the specs themselves. In CI the job's env is the only source and `tests/setup.ts` has no defaults. Never write a password in code, a script or a doc.
- **Time zone:** compute "today", the weekday and the clock time with `src/lib/format-date.ts` (`APP_TZ`: `toISODate`, `weekday`, `appTime`), on the server and in client components alike; a day is shown as `DD.MM.YYYY` with `formatDMY` and as `DD.MM` (a chart's day label) with `formatDM`, never a hand-written split, in specs too. Never `new Date()` day math or a device-local API (`getDay`, `getHours`, `toTimeString`, `toLocaleDateString` without `timeZone`, and the like): the server runs in UTC and a device can be anywhere. `tests/format-date.test.ts` scans `app/` and `src/` and fails on them. `public/sw.js` and `scripts/seed-dev.cjs` are outside the scan.
- **New table:** add a GRANT for `life_tracker_app` in the migration, or the app cannot use it.
- **Postgres version:** pinned in four places that must match: `.github/workflows/ci.yml`, `.github/workflows/backup.yml`, `docker-compose.yml`, `scripts/backup-now.sh`.
- **Service worker cache:** the cache name in `app/components/page-cache.ts` must match `PAGES` in `public/sw.js`; bump `CACHE` in `public/sw.js` to refresh the muscle model.
- **Manual scripts:** `scripts/backup-now.sh` (plaintext dump of the live database into `.local/backups/`) and `scripts/import-personal.cjs` (wishlist and tasks from `.local/personal-data.json`) have no npm script or caller on purpose (D-008). Only the owner runs them, with `DATABASE_URL_MIGRATE` typed into a hidden prompt; never run them yourself. A change to `wishlist_items`, `todos` or `item_categories` must also update the importer.
- **Backup workflow:** `.github/workflows/backup.yml` must not be weakened; the private `age` key stays with the owner.
- **Health data:** never sent to an AI provider.
- **iOS 26 bottom bar:** Safari draws nothing fixed under its bottom bar and fills that strip with the plain page color, so a fixed layer near the bottom edge (the glow) looks cut off; on a screen that never scrolls, make it `position: absolute` (D-032).
- **e2e server:** the server also gets `NEXT_PUBLIC_CLAUDE_ENABLED=true` and a throwaway `CLAUDE_TOKEN_KEY` (made from a fixed string in the config, not a secret), because the Claude card on `/settings` renders only with the flag (D-017); the flag also shows the Assistant tab on `/health` in every spec, and no spec opens that tab (it needs the `claude` CLI). `AUTH_DEV` throws under a production build, so `npm run e2e` starts `next dev` on port 3100, or `E2E_PORT` when set so parallel worktrees each run their own server (not `next start`) with `AUTH_DEV=true` and the local test database; the config takes `DATABASE_URL` from `tests/setup.ts` and refuses a non-local host (`CI=1` with a remote `DATABASE_URL` could otherwise reach a real database). It fails at start with Next's own message while another `next dev` runs in the same folder (stop `npm run dev` first). `next dev` also re-creates an `AGENTS.md`; it is in `.gitignore`, never commit it. `.dockerignore` lists `playwright.config.ts` because it imports `tests/setup.ts` (also ignored) and the image's `next build` typechecks every `**/*.ts` it can see; keep both ignored together. Vitest excludes `tests/e2e/**`; lint ignores `test-results/` and `playwright-report/`.
- **e2e cleanup and shared database:** the app role cannot delete users, so the `signedInPage` fixture deletes its user with `DATABASE_URL_MIGRATE` (the owner role, as the Vitest tests do); the config refuses a non-local host for both URLs. `npm run e2e` and `npm test` in one folder share its test database, and several Vitest files empty it (`resetDb` in `tests/db.ts`, `TRUNCATE TABLE users CASCADE`): a Vitest run in the same folder during `npm run e2e` deletes the spec's user, and the add fails with a foreign-key error (`Failed to save item`). The Stop hook's `npm run check` is such a run: an agent that starts `npm run e2e` in the background and ends its turn breaks a random signed-in spec, so it waits for the run in the same turn. `npm run e2e` cannot start while `npm run dev` runs in the same checkout (Next allows one dev server per folder); to keep the owner's dev server up, commit and run it from a temporary `git worktree add --detach .claude/worktrees/<name> HEAD` beside it (`.env` copied, `node_modules` cloned with `cp -c -R`, not symlinked: Turbopack rejects that), then remove it and drop its `life_tracker_test_<name>` database. Run them one after the other; to run both at once, point the e2e run at its own local database (`CI=1` with both `DATABASE_URL` and `DATABASE_URL_MIGRATE` set to it). Another worktree's run no longer interferes (D-018).
- **e2e sign-in:** sign in through `/api/auth/csrf` and `/api/auth/callback/credentials` (`signIn` in `tests/e2e/helpers.ts`), not the `/signin` form. It is faster, and a spec about the form itself signs in through it (`tests/e2e/navigation.spec.ts`). On that page the first `/api/auth/session` calls (two under React StrictMode in dev) can each set a different CSRF cookie, so a token read in between is refused: NextAuth answers 200 with `csrf=true` in its url and no session. The form therefore keeps Continue, the GitHub button and the name field unusable until its session check has answered (`useSession().status`) or 5 s have passed without an answer (`SESSION_CHECK_WAIT_MS`), and tries a refused sign-in once more before showing "Failed to sign in"; a spec waits for Continue to be enabled (Playwright's `click` does), never with `networkidle` or a time.
- **Zod messages:** `z.config({ customError })` in `src/lib/validations/result.ts` is global and gives the people's messages only where a schema has none of its own; a schema's own `message` wins.
- **React error #441 in a 500 page's console:** expected. Next's `onCaughtError` logs every error an `error.tsx` boundary catches, in production with the message left out; its digest matches the page's Reference. Our `error.tsx` logs nothing.
- **Production session cookie:** `__Host-next-auth.session-token` (`src/auth.ts`); Playwright's `addCookies` refuses a `__Host-` cookie on http, so a spec against `next dev` uses the dev name.
- **Scroll anchoring in specs:** Chromium keeps a list in place when rows above it change; iPhone Safari has no anchoring. `.list-box` sets `overflow-anchor: none`, and a spec that checks a slide turns it off (`slideLikeSafari()` in `tests/e2e/categories.spec.ts`).
- **Ending a tap burst in a spec:** `page.keyboard.press("Shift")` ends `useOnce`'s burst (a key press ends it), so a setup click right before the tested tap is not swallowed.
- **A toast across a round trip in a spec:** a toast lasts 5 s of the page's clock, and under load one refresh or another device's load can take longer (7-8 s seen), so a spec that checks or taps a toast after a refresh or another device's steps holds that page's clock (`pauseClock`, `installStoppedClock`) and moves it only as far as needed (`runFor`, `refreshesDone(page, { tick })`, `refreshOnStoppedClock` in `tests/e2e/gym.spec.ts`), never `clock.resume()`, which runs in real time. Likewise, before a reload wait for the answer of the last write sent, not the first: actions go one at a time, and a reload aborts the one on its way.
- **Back online in a spec:** Chromium's offline emulation (`Network.emulateNetworkConditions`, what DevTools' Offline does) can tell the page "online" before the page's requests get through: a request its "online" handler sends at once can still fail as disconnected (a probe: 3 of 480, 2 of them the first time back online), and the app then waits for the next focus, minute or "online" (D-034), past the spec's timeout. A spec that checks what the page does once back online uses `backOnline` in `tests/e2e/app-shell.spec.ts`: it stops the page's clock, goes online, waits until a request of the page's own gets through, then lets the clock go on.
- **Agent worktrees:** an agent run with `isolation: worktree` may branch from `main`, not the feature branch; its brief starts with `git merge --ff-only <branch>` (or `git reset --hard <branch>` in a fresh worktree) and checks the commit.
- **`.env` in worktrees:** the main folder's `.env` may point at the live database, so nothing copies it into a worktree (D-045; `.worktreeinclude` was removed, and a workflow update must not bring it back). A worktree that needs one copies `.env.example`.
- **Other worktrees:** `.claude/worktrees/**` carry their own test copies, so Vitest excludes `.claude/worktrees/**`; lint, typecheck and the Docker context exclude all of `.claude/`.
- **Language server:** the `typescript-lsp` plugin needs the global npm packages `typescript-language-server` and `typescript` (`npm install -g --ignore-scripts typescript-language-server typescript`). Installed on the owner's Mac on 2026-11-18.
