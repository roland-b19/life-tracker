# Decisions: general

Newest at the bottom. Entry format: `.claude/skills/maintain-kb/assets/decisions.md`. Superseded and obsolete decisions move to `archive/decisions.md`.

## D-001: Run live on Vercel + Neon; keep Azure for course demos only (2026-11-18)
- **Why:** Cost: Vercel and Neon free tiers cost nothing, Azure costs money. Simplicity: less infrastructure to run for one user. Recorded from the owner's answer on 2026-11-18; the move itself happened earlier in November 2026.
- **Rejected:** Running the app on Azure permanently (costs money, more to operate for personal use).
- **Status:** active. Consequences: push reminders are off on the Vercel variant (the worker needs Azure Storage Queue), and the free-tier query budgets are tested ([domain](../domain.md)).

## D-002: One check command, `npm run check`, run by the Stop hook and CI (2026-11-18)
- **Why:** The verify skill needs one headless command; CI runs it as written. It chains lint, typecheck, Vitest and the KB check, so the local hook and CI give the same answer. Vitest stays (golden rule 1: it was already the runner).
- **Rejected:** A check without tests (faster, but hides DB regressions); no Stop hook until Postgres runs locally (checks would only run in CI). The owner chose the full command and will start Postgres with `docker compose up` when working.
- **Status:** active. The end-to-end tool was chosen later in D-005. Screenshot tests were not requested.

## D-003: Keep `azure-preflight.sh` and the unused schema columns (2026-11-18)
- **Why:** `scripts/azure-preflight.sh` is a manual tool for the Azure course demos (D-001), like `backup-now.sh` and `import-personal.cjs` (D-008). The columns `daily_metrics.notes`, `workout_split_days.order_index` and `workout_splits.is_active` may hold rows in the live database, and migrations are additive only; dropping them needs a migration the owner runs. Both chosen by the owner on 2026-11-18.
- **Rejected:** Deleting the script (the demos need it); dropping the columns now (risk to live data for no gain).
- **Status:** active. A column is removed only in its own change, after a search proves nothing reads it.

## D-004: CI blocks on production dependency advisories only (2026-11-18)
- **Why:** The picomatch advisory GHSA-fc5q-39xc-vjpf (high) covers every published version and has no fix; only dev tools (vitest, vite, eslint, drizzle-kit) pull picomatch in. `npm audit --omit=dev` finds 0 vulnerabilities. A full audit as a blocking step kept `main` red from 2026-11-17. Chosen by the owner on 2026-11-18 (PR #134).
- **Rejected:** Waiting for an upstream patch (weeks, `main` blocked meanwhile); `npm audit fix --force` (downgrades vitest to 3.1.4); bypassing branch protection.
- **Status:** active. The full audit still runs as a report-only step (`continue-on-error`). Revisit when picomatch has a fixed release.

## D-005: End-to-end specs with Playwright Test on `next dev`, Chromium desktop and phone (2026-11-18)
- **Why:** The verify skill already prescribes Playwright Test (golden rule 1), and it adds a real browser check for the UI flows Vitest cannot see. Specs run against `next dev` because `AUTH_DEV=true` throws under `NODE_ENV=production`, so `next start` cannot sign in. Targets follow the conventions page: Chromium at desktop size and at 375px. `@axe-core/playwright` scans every page a spec visits. `npm run e2e` stays out of `npm run check` so the Stop hook stays fast; CI runs both. Chosen by the owner on 2026-11-18 ("all recommended, axe included"); the first spec is the Wishlist flow ([plan](../archive/plans/e2e-first-spec.md)).
- **Rejected:** Cypress or Vitest browser mode (heavier or still needs Playwright, no gain); Firefox and WebKit projects (slower CI, the KB targets are Chromium only); running specs against a production build (AUTH_DEV forbids it); the dev database `life_tracker` (test data would mix with seed data); e2e inside `npm run check` (a browser run at every stop).
- **Status:** active.

## D-006: Local test credentials live only in `.env.example`; no fallback hosts in the Azure scripts (2026-11-18)
- **Why:** `tests/setup.ts` repeated the local Docker passwords from `.env.example`, and its CI branch repeated the CI Postgres password from `ci.yml`. Now `tests/setup.ts` parses `.env.example` (`util.parseEnv`) and builds the superuser migrate URL from it; in CI it requires the job's env and has no defaults. `azure-migrate.sh` no longer reads a `postgres_server` override that nothing set: the host is the bicep name `lifetracker<env>pg`, and `db-init.cjs` requires `DB_HOST` instead of defaulting to the stage server, so a run cannot reach another environment's server. `infra-contract.test.ts` pins both. Asked by the owner on 2026-11-18.
- **Rejected:** Reading `.env` in the tests (it may hold live URLs, so tests could reach a real database); a second copy as defaults in `docker-compose.yml` (another duplicate); keeping the CI fallbacks (a stale copy of `ci.yml`).
- **Status:** active. Not changed: `DB_APP_PASSWORD` in `db-init.cjs` is also unset by every caller; it was outside the question asked.

## D-007: Weight is a server action, not a REST API (2026-11-18)
- **Why:** Golden rule 1: weight was the only JSON API (its commit predates the server-action convention) and nothing recorded a reason to keep it. Chosen by the owner on 2026-11-18. The weight card calls `saveWeightAction`, `deleteWeightAction` and `restoreWeightAction` in `src/actions/food.ts`; data access and schemas moved into `src/lib/food.ts` and `src/lib/validations/food.ts`. Saving sets the day's weight on the server (create, or change the row the day already has, and report the replaced row), which replaces the client's 404/409 retry sequence. Undo of an edit saves the old value again; Undo of a delete restores under the old id. Next checks the Origin of every server action call, so `isSameOrigin`, the generic API error body and the request logger (used only by weight) were deleted.
- **Rejected:** Keeping the routes for a possible future client (no second client exists); separate create and update actions (the stale-screen cases need a lookup first).
- **Status:** active. Saves take the per-user advisory lock (`lockUser`, scope `weight`), so two saves of the same new day at once become a create and an edit instead of a unique violation.

## D-008: Keep `backup-now.sh` and `import-personal.cjs` as manual owner tools (2026-11-18)
- **Why:** Neither script has an npm script, a CI step or a test, but both are deliberate: `scripts/backup-now.sh` takes one plaintext `pg_dump` of the live database into the gitignored `.local/backups/` before a data-changing step (the weekly encrypted workflow is separate), and `scripts/import-personal.cjs` loads the owner's wishlist and tasks from the gitignored `.local/personal-data.json`. Both carry a header comment with their usage, and the importer was updated for schema changes as late as 2026-11-15. The `bash -n scripts/*.sh` CI step still syntax-checks `backup-now.sh`, and `backup-now.sh` is one of the four places that pin the Postgres version. Chosen by the owner on 2026-11-18, one answer per script.
- **Rejected:** Deleting `backup-now.sh` (the Postgres version cross-references in `ci.yml`, `backup.yml` and `docker-compose.yml` would then need editing, and the manual copy before data changes would be lost); deleting `import-personal.cjs` (the owner wants to keep it).
- **Status:** active. The owner runs both from their Mac with the owner URL in a hidden prompt; no agent runs them. `import-personal.cjs` must follow schema changes to the tables it writes.

## D-009: One name for form error state: `errorMsg` (2026-11-18)
- **Why:** Golden rule 1: client forms used `error` (6 files), `formError` (2) and `titleError` (1) next to `errorMsg` (Wishlist and Settings). The Wishlist page is the reference, so its name wins over the majority. Every client form now declares `[errorMsg, setErrorMsg]`.
- **Rejected:** `error` (the most used, but it also names the `FormModal` prop and the `error` field of action results, so it reads ambiguously in a handler).
- **Status:** active. The `error` prop of `FormModal` is unchanged.

## D-010: One answer for every server action: zod `.parse()` inside `respond()`, `{ success, error }` for failures (2026-11-18)
- **Why:** Golden rule 1: actions validated four ways (throwing `.parse()`, `check()` in gym, `safeParse`, hand-written checks in `food.ts`) and failed four ways (thrown Error, `{ success: false, error }`, gym's `GymRefusal`, `null`). Chosen by the owner on 2026-11-18. In production Next hides the message of a thrown server-action error, so a refusal the user should read has to be returned as data. `respond(run)` in `src/lib/validations/result.ts` returns `{ success: true, ...what run returns }` or `{ success: false, error }`; a failed zod `.parse()` and a `Refusal` (the one class for an expected refusal, also used by `src/lib/gym.ts`) become the failure, and the first zod issue's message is the `error`. `requireUser()` and the feature-flag guards run before `respond` and still throw, so anonymous calls reject as before (`tests/actions-anonymous.test.ts`); so does anything unexpected, such as a database error or a lib-level "not found or unauthorized" Error. Every action goes through `respond`, even one that takes no input and cannot refuse, so the answer always has the same shape. Deleting a row that is already gone (todo, meal) is not a failure: it returns success with `deleted` empty. Clients read `.success` and show `.error` (`role="alert"`); a `.then(() => true, () => false)` would now report success on a refusal.
- **Rejected:** Throwing everywhere (the browser would show only a generic message in production); `safeParse` everywhere (a result check after every parse, easy to forget); a `check()` helper (a second validation vocabulary beside zod); returning `null` for "not found" (no message, so the user sees a generic failure); one class of Error caught on the client (the message is hidden in production).
- **Status:** active. `src/lib/food-ai-chat.ts` still uses `safeParse` on each meal the model proposes: it skips a bad meal instead of answering a caller, so it is not an action (left as it is).

## D-011: One session guard for pages: `requirePageUser()` (2026-11-18)
- **Why:** Golden rule 1: five pages each repeated `getServerSession(authOptions)` plus their own `redirect("/signin")`, and `RequireSession` repeated it again, next to `requireUser()` for actions. The pages need the user id and name to read data, and a layout cannot pass props to its page. The checks must stay on every page: a layout does not render again on client navigation, so it cannot be the only guard (Next's authentication guide: check close to the data). `requirePageUser()` in `src/server/auth.ts` shares one session reader with `requireUser()` and returns `{ id, name }` (name defaults to `"User"`) or redirects to `/signin`; `RequireSession` calls it too.
- **Rejected:** Removing the page checks and trusting the layouts (client navigation skips the layout, so a page could render data for an anonymous session); a `getSessionUser()` that returns null and leaves the redirect to each page (the redirect would be repeated again, and a page could forget it).
- **Status:** active. `tests/pages-auth.test.ts` calls every page and layout as an anonymous visitor and fails if one does not redirect or touches the database.

## D-012: Tasks e2e spec: the Today flow plus the space and tab split, checked in the database, one shared settle helper (2026-11-18)
- **Why:** Tasks (`/todos`) is the next page after Wishlist and the weight card to get a browser check (D-005). It opens on the Daily tab, so the spec switches to Today for the one-off flow: add, complete and Undo, edit and Undo, delete and Undo, with the Progress card. A second test adds a daily task and checks it shows only on Daily of its own space (not on Today, not under Business), because the page keeps both spaces and both lists in one client state. After each write the spec waits for the server action's answer and reloads, as the weight spec does: Tasks deletes optimistically, so the screen alone would pass while the database lost the write. `andSettle` moves from `weight.spec.ts` to `tests/e2e/helpers.ts` so both specs share one copy (golden rule 1). One `@a11y` test scans `/todos` with a task listed, then with the New task form open, on both projects. Chosen by the owner on 2026-11-18 ("all recommended"), in `tests/e2e/tasks.spec.ts` ([plan](../archive/plans/e2e-tasks-spec.md)).
- **Rejected:** Only the Today flow (does not prove the space and tab split); also the categories card (a feature of its own with much code, better as its own spec); screen-only checks without a reload (miss a lost write); a second copy of `andSettle` (two ways); scanning the Daily tab too (little gain while categories stay out); a job timeout in `ci.yml` (not needed, and it would raise the PR to the High tier).
- **Status:** active. Out of every variant: the reminder field and "Task reminders" card (`NEXT_PUBLIC_PUSH_ENABLED` is off in e2e), carried-over tasks (they depend on yesterday's data), Gym.

## D-013: Layout of logic: `src/actions`, `add...` names, `/health`, no `revalidatePath` (2026-11-18)
- **Why:** Golden rule 1: four deviations were tracked as deprecated patterns; the owner chose to migrate all of them in one change. (1) Server actions moved from `src/app/actions` to `src/actions`, so `src/app/` no longer sits next to the root `app/` (imports are `@/actions/...`). (2) Every function that adds a row is `add...`: `createTodo`, `createTodoAction`, `createCustomExercise(Action)`, `createWorkoutSession` and the schemas and input types `createTodoSchema`, `createWishlistItemSchema`, `createShoppingItemSchema`, `createCustomExerciseSchema`, `createSessionSchema` became `add...` (`startSessionAction` keeps its name: it is the user's word). (3) The page route is `/health`, matching the Health label; `next.config.ts` redirects `/food` and every sub-path to `/health` for good (308), so old bookmarks and the installed app keep working, and the service worker and `/` used `/health` as the start (since 2026-11-19 they start on `/todos`, D-028). The liveness route moved from `/health` to `/api/health` (Dockerfile healthcheck and the Azure liveness probe in `infra/main.bicep` follow; the files are edited only, nothing was deployed). (4) `revalidatePath` is gone from the gym actions, so every action follows the same pattern; the client keeps its state and `app/providers.tsx` refreshes the router cache once writes stop.
- **Rejected:** Leaving `/food` as the route and renaming the label (the owner wants "Health"); keeping `/health` as the liveness route and putting the page elsewhere (the name belongs to the page; `/api/*` is where routes that serve no page live); no redirect (breaks bookmarks and the installed app); renaming `startSessionAction` to `addSessionAction` (it starts a workout, it does not add to a list).
- **Status:** active. The Azure container app still probes `/health` until the owner redeploys it from the new `infra/main.bicep`; the Azure setup is torn down and deployed only on request. `public/sw.js` caches pages under the new path, and its page cache is now `life-tracker-pages-v2`, so the new worker deletes the old one (with the pages stored under `/food`) when it activates. The `food` names of `app/health/food-client.tsx`, `src/actions/food.ts`, `src/lib/food.ts` and `src/lib/validations/food.ts` stay on purpose: Food is the feature (a tab of the Health page), Health is the page.

## D-014: Gym e2e spec: the workout, cancel, routine and custom-exercise flows checked in the database, days picked by name, no 3D map flow (2026-11-18)
- **Why:** Gym (`/gym`) is the next page after Wishlist, the weight card and Tasks to get a browser check (D-005, D-012). Five tests in `tests/e2e/gym.spec.ts`: one `@a11y` scan on both projects (the page, the "Edit" day dialog, a started workout) and four flows on `desktop`: start a workout, log a set, finish it and reopen it with Undo; log a set and cancel the workout with Keep/Delete and Undo; edit a training day with a new exercise created in the editor and Undo of the save; create a custom exercise, delete it from "My exercises" and Undo. Each write waits for the server action's answer with `andSettle` and is checked again after a reload, as in D-012. The seeded split has rest days that move with the date, and the page selects today's day at load, so the spec always picks a day by its name ("Upper (chest)") and never relies on "Today". No new helper: `andSettle` and `expectNoSeriousViolations` are enough. The owner delegated the design choices to the recommended options on 2026-11-18 ([plan](../archive/plans/e2e-gym-spec.md)).
- **Rejected:** Driving the 3D muscle map (WebGL may be missing in CI, and the chips beside it are a second way to the same selection: a feature of its own); excluding the map from the axe scan (nothing is excluded, D-005); testing the deload card and the progress chart in this change (separate features, little gain until they change); picking the day the page selects today (the spec would depend on the weekday); renaming a custom exercise (not what the owner uses; the add and remove cover the Undo path); one big test for everything (a failure would hide which flow broke, and one user's state would leak between flows).
- **Status:** active. Out of every variant: the deload card, the progress chart, the muscle map, drag-to-reorder.

## D-015: Health e2e spec: the Today and Shopping tabs in four flows, checked in the database; no day stepper, no Assistant tab (2026-11-18)
- **Why:** The weight card has its own spec; the rest of `/health` has none (D-005). Modelled on Tasks (D-012): each flow runs its writes through `andSettle`, checks the Undo, and reloads to prove the database holds the same state, because Shopping toggles and deletes are optimistic (the screen alone would pass while a write was lost). Four desktop flows: a meal (log, delete, Undo of each); the nutrition goals (edit, Undo); water and steps (a quick tap and its Undo, a set value with a changed goal and its Undo, steps); the Shopping list (add, edit, tick, delete, clear bought, Undo of each). The Assistant tab renders only with `NEXT_PUBLIC_CLAUDE_ENABLED=true` (a local `.env` may set it, CI does not) and its action runs the `claude` CLI, so the spec never opens it and never asserts it is absent. Chosen with the owner's delegation on 2026-11-18 (every recommended option; the owner approves the finished plan), in `tests/e2e/health.spec.ts` ([plan](../archive/plans/e2e-health-spec.md)).
- **Rejected:** One long test for the whole page (the first failure hides the rest, and an Undo chain gets hard to follow); a test that asserts the Assistant tab is missing (the result follows the machine's `.env`); a spec that sets the flag on and mocks the model (a second way to fake a service, and it would exercise the CLI path); a past-day test by writing rows with SQL (there is no UI for a past day); the two Shopping Categories cards (their own spec, in another session); a time-based wait for the water or steps toast (auto-retrying `expect` is the project's way); changing `playwright.config.ts` to force the flag off (not needed when the spec never depends on it).
- **Status:** active. Out of every variant: the weight card (`weight.spec.ts`), the categories and units cards, the Assistant tab, edits of past days.

## D-016: Categories e2e spec: one shared flow run on Wishlist, Tasks Daily and Health shopping (2026-11-18)
- **Why:** The categories card (`app/components/categories-card.tsx`) is one component used by Wishlist, the Tasks Daily list and the Health shopping list (twice there: categories and units), saving through two sets of actions (`src/actions/categories.ts` by scope, the shopping actions in `src/actions/food.ts` by kind). D-012 left it out of the Tasks spec as its own spec. One file, `tests/e2e/categories.spec.ts`, holds one flow driver written once and run per page, so the three pages cannot drift apart (golden rule 1): add a category and Undo it, rename with Undo, a rename onto an existing name (a merge) with Undo, and a delete of a category that holds an item (the item moves to Other) with Undo, each checked in the card, in the item's group heading and again after a reload, so a write the optimistic screen hid would fail. Each write goes through `andSettle` with a piece of the request body (Tasks reloads its list after every write). Shopping is cheap because the card is the same: only the item form differs. One `@a11y` test per page scans with the Edit and then the New category form open, on both projects. Chosen by the owner's delegation on 2026-11-18 (the recommended option of each choice).
- **Rejected:** Wishlist only (leaves the Tasks and shopping action sets unchecked: three different server paths); a copy of the flow per page (three ways to do one thing); a table-driven `test.describe` loop generated at import (hides which page failed in the title; plain tests that call one driver read better); also reorder, fold, units and refused names in the same spec (each is its own behaviour, not the add, rename, delete and Undo core; listed in the plan's Out); moving the driver into `helpers.ts` (it is only this spec's; `helpers.ts` is shared with three other sessions' specs).
- **Status:** active. Out: the Units card, drag and keyboard reorder, folding a group, duplicate and "other" name refusals, any app code change.

## D-017: Settings e2e spec: the e2e server turns the Claude flag on with a fake key; the spec covers the Claude card and the data export (2026-11-18)
- **Why:** `/settings` holds only the Claude connection card and returns 404 unless `NEXT_PUBLIC_CLAUDE_ENABLED=true` (a build-time flag), and the card needs `CLAUDE_TOKEN_KEY` (32 bytes, base64) to encrypt a token. So `playwright.config.ts` sets both on the `next dev` server: the flag `true` and a throwaway key made from a fixed string (not a secret, e2e only, like `NEXTAUTH_SECRET`). The token is only stored encrypted, never sent to Claude, so a fake `sk-ant-...` value is enough and no external service is called. The spec (`tests/e2e/settings.spec.ts`) follows D-012: the Claude card flows with Undo, each checked after a reload (connect, the refusal of a malformed token, replace the token, disconnect), and the data export, which is a button in the navigation menu (Settings is where the domain places it) and ends in a browser download: the spec asserts the download event (file name) and reads the file in memory to check that it holds the user's data and not the token. One `@a11y` test scans `/settings` not connected, with the connect form open, and connected, on both projects. Owner delegated the choices on 2026-11-18 ("use the recommended option of each"), in `tests/e2e/settings.spec.ts` ([plan](../archive/plans/e2e-settings-spec.md)).
- **Rejected:** Leaving Settings out because the flag is off (the page and its Undo flows would stay unchecked); a second dev server with the flag on, only for this spec (twice the start time and a second port for one page); a flag set per test (it is inlined at build, a spec cannot change it); testing the flag-off 404 in the browser (needs the second server; `tests/pages-auth.test.ts` and `tests/features.test.ts` cover the flag in Vitest); comparing stored ciphertext before and after Undo (needs a database read of secrets in the spec; `tests/claude-connection.test.ts` covers it); asserting the export file's full text (it changes with the clock; only its shape and the token's absence are stable).
- **Status:** active. Note (2026-11-19, D-024): Settings is now always shown, with the Appearance card; only its Claude card needs the flag, the flag no longer hides the page or its navigation link, and `tests/pages-auth.test.ts` checks that with the flag off the page renders without reading the connection. The flag also shows the Assistant tab on `/health` in every spec; no spec clicks the Assistant tab (it needs the `claude` CLI). Note (2026-11-19, D-028): the data export is removed, and its test with it; the spec covers the Claude card and the Appearance switch. Out of every variant: push (the Settings page has no push card; reminders live on Tasks and need `NEXT_PUBLIC_PUSH_ENABLED`, off in e2e), the flag-off page (Vitest covers it), a real Claude token or call.

## D-018: One test database per worktree, created and migrated by a global setup; `AGENTS.md` ignored (2026-11-18)
- **Why:** Vitest files `TRUNCATE ... users CASCADE`, so two sessions testing on `life_tracker_test` at once delete each other's rows: the Stop hook's `npm run check` failed with foreign-key errors and empty lists that were not real failures. Now `tests/local-db.ts` names the local database after the checkout: `life_tracker_test` in the main folder, `life_tracker_test_<worktree name>` in `.claude/worktrees/<name>`. `tests/global-setup.ts` (Vitest `globalSetup` and Playwright `globalSetup`, skipped in CI) creates it when missing, applies the grants of `docker/postgres/init.sh` and runs the Drizzle migrations, so a new worktree needs no manual step and the old "migrate the test database once" command is gone. `tests/setup.ts` takes both URLs from the same helper. `next dev` re-creates `AGENTS.md` on every start, so `/AGENTS.md` is in `.gitignore` instead of being deleted by hand. Chosen by the owner on 2026-11-18 (my recommendation).
- **Rejected:** A shell script or npm `pretest` hook that creates the database (the name would be derived twice, in a script and in `setup.ts`); a random database per run (leaves one behind per run; the name must stay stable between `npm test` and `npm run e2e`); one schema per session in the shared database (the app's tables and the migrations assume `public`); a lock so sessions take turns (slow, and a stuck session blocks the rest); committing `AGENTS.md` (Next rewrites it, so every start dirties the tree).
- **Status:** active. The `DATABASE_URL_TEST` shell override is gone (it sent the owner's truncates to the shared DB, see the old note); `CI=1` with both URLs set still selects any database. A worktree's database stays after the worktree is removed: drop it by hand (conventions).

## D-019: Axe scans wait for the refresh a write left due, not only for a title (2026-11-18)
- **Why:** `document-title` flaked twice: #160 waited for the title, then it failed again on `phone` in the categories spec (CI run 44387997885). The Playwright trace of that failure shows `<head>` with its `<title>` gone at the moment axe ran: the Save of the previous step had sent a server action, and `app/providers.tsx` refreshes the router 600 ms after the last one (D-013). Each `router.refresh()` removes and re-adds the metadata tags React hoists into `<head>`, twice; on a fast machine that happens inside one task, on a slow runner it can span several, so the `toHaveTitle` check that passed just before the scan proves nothing about the scan. Now the `signedInPage` fixture tracks the page's action POSTs and its refresh GET (`watchRefreshes`), and `expectNoSeriousViolations` waits (auto-retrying `expect.poll`) until no refresh is due, then for a `<head>` that did not change for one animation frame, then for the title. Not reproduced locally in 45 runs of the old helper; the refresh behaviour was recorded with a MutationObserver, and a throwaway probe that removes the title during the refresh and puts it back 400 ms after its response failed the old order and passed the new one (it failed again with the new wait removed).
- **Rejected:** A retry of the scan (hides the finding; D-005); excluding `document-title` or `<head>` from axe (D-005, nothing is excluded); a sleep after each write (time wait, and the refresh time depends on the runner); changing `andSettle` to wait for the refresh (every flow would pay about 600 ms, and only the scans need it); turning the app's refresh off in e2e (the specs would stop running the real page); changing `app/providers.tsx` or the metadata (the app is right: a refresh may rebuild the head).
- **Status:** active. Amends D-012 (`andSettle` stays as it is). The tracker covers the `signedInPage` pages; the anonymous sign-in scan has no write.


## D-020: New look: slate surfaces with one turquoise accent, a dark and a light mode that follow the system or a manual switch (2026-11-19)
- **Why:** The owner opens the app all day (food, gym, tasks) and found the Graphite look "flat, monochrome, not alive": it said "no rush". ## D-027: A stranded page request can no longer freeze the app; a phone exports through the share sheet (2026-11-19)
- **Why:** On the owner's iPhone (the Home Screen app), after Export data the app stopped responding: links and actions did nothing (the More button still opened its menu), and a browser bar appeared at the bottom. Two causes. (1) The export saved the file through an `<a download>` link to a `blob:` URL, which in a Home Screen app opens a file viewer over the page and leaves the bar. (2) The export is a server action, so `app/providers.tsx` sent `router.refresh()` 600 ms later, while iOS covered the page; iOS can strand a request a covered or backgrounded page sends ([WebKit 315804](https://bugs.webkit.org/show_bug.cgi?id=315804), [211018](https://bugs.webkit.org/show_bug.cgi?id=211018)), and the router keeps every later navigation and action waiting behind a refresh with no answer (reproduced in Chrome by holding that request: a tab fetched its page and never showed it). Fixes: (1) on a touch screen (`(pointer: coarse)`, as `app/gym/muscle-map.tsx` detects it) that can share files (`navigator.canShare({ files })`), the export calls `navigator.share()` with the `.txt` as a `File` (Save to Files); closing the sheet (`AbortError`) shows no toast; elsewhere the download link stays. (2) The refresh is sent only while the page is visible and has the focus, else at its next `focus` or `pointerdown`; and `withRouterTimeout` (`app/components/router-fetch.ts`, wrapped around `fetch` in `app/providers.tsx`) aborts a router page request (an RSC GET, not a prefetch or an action) with no answer after 10 s, on which Next loads that page the normal way, so any other stranded request (a tap just before the app went to the background) also ends in a reload instead of a freeze (`tests/router-fetch.test.ts`).
- **Rejected:** moving the export to a GET route (server actions are the one way for reads too, such as `loadTodosViewAction`, and any other action leaves the same refresh); dropping the refresh after writes (other tabs would open stale from the router cache, D-019); reloading on `pageshow` or `visibilitychange` (a reload loses the page's state, and the stranded request is not tied to those events); the share sheet on every device (a desktop that can share would lose the plain download, and the e2e spec checks the download).
- **Status:** superseded by D-028: the freeze came back on the owner's iPhone with these fixes in, so the export was removed, and the share sheet, the focus gate and `withRouterTimeout` (unproven) went with it
