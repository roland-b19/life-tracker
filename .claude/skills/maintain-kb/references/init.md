# Init: build the knowledge base

1. If `docs/kb/` already exists, don't overwrite it. Run **Update** from the maintain-kb skill instead. For an existing codebase, first run the audit-project skill (initial cleanup), so the KB describes clean code and records the agreed patterns and tracked migrations.
2. Create the layout from the templates in `.claude/skills/maintain-kb/assets/`:
   - `INDEX.md`, `domain.md`, `architecture.md`, `conventions.md` and `status.md` from the template of the same name; `decisions/general.md` from `.claude/skills/maintain-kb/assets/decisions.md`, with `general` as its area (split it by area as it grows, rule 6)
   - `log/<current YYYY-MM>.md` from `.claude/skills/maintain-kb/assets/log-month.md`
   - Create `archive/` only when something first needs archiving.
   - Add the line `docs/kb/log/*.md merge=union` to the project's `.gitattributes`, creating it if it's missing, so log entries appended on two branches merge without a conflict.
3. Fill in the content. Follow the rules in the maintain-kb skill, especially the first: store the why, not the what. In each page's frontmatter, `covers` lists the repo-relative globs of the code the page describes (delete the line if none); the check script uses it to flag pages whose code changed after `last_verified`.
   - **New project:** take the goal, users, product and domain knowledge, scope, constraints, decisions so far (with the rejected alternatives) and the user's working preferences from the conversation. If the goal or key constraints haven't been stated, ask with AskUserQuestion (at most 4 questions).
   - **Existing codebase:** give the exploration to an Explore subagent, so file dumps stay out of this session's context. Ask it for the purpose, the main components and how they connect, entry points, build and test commands, and notable patterns. Write `architecture.md` from its summary, splitting off a topic page for any part that would push it past 250 lines, with `covers:` globs on each page. Record only what the code can't tell you. Don't guess at intent you can't derive ("why X over Y", what the product is for, domain rules): ask the user, or list it as an open question in `status.md`. `domain.md` usually needs the user, since code shows rules but rarely their reasons.
   - **Existing docs:** list the README, `docs/`, architecture decision records, `AGENTS.md` and similar files. Move their durable facts into the KB with the user, and ask whether existing decision records become `D-NNN` decisions.
   - **Conventions:** the template comes with defaults (when the user is away, merge on green off, the risk tier lists). Show them to the user and keep only what they confirm.
   - **Claude's auto memory** (`~/.claude/projects/<project>/memory/`): move any project facts into the KB, then reduce those memory files to a pointer to the KB, so each fact has one home.
4. Add the snippet from `.claude/skills/maintain-kb/assets/claude-md-snippet.md` to the project's `CLAUDE.md`, creating the file if it's missing. If `CLAUDE.md` has no `# ` title line, add `# <project name>` at its top. Keep the import line exactly `@docs/kb/INDEX.md`. Offer to move into the KB any other line Claude doesn't need in almost every session.
5. Install the reminder hook: merge `.claude/skills/maintain-kb/assets/hook-settings.json` into the project's `.claude/settings.json`, keeping any hooks already there. The hook costs no tokens unless there's unrecorded work: it keeps KB facts in compaction summaries, asks for an Update right after a compaction, and flags a session that ended without one at the next session start. Tell the user that a session started before the settings file existed won't load it until restarted.
6. Write the first log entry. If an initial cleanup ran first, include its `Audit clean at <short commit hash>` line, so the next audit starts from there. Run the check script and fix any errors.
7. Report the pages created and the open questions recorded.
